# API-5A/A1 — third-party source coverage and code-independence matrix

**Research date:** 2026-10-28 (repository revision lookup and static source reading).  
**Scope:** Orbit B-hyve **cloud** REST and WebSocket implementations; no BLE-only sources and no FreeBSD bhyve virtualization.  
**Status:** A1 source/revision/ancestry baseline. This is **not** a live validation, API endpoint contract, or API-5A completion claim. **No live Orbit API requests were made during A1.**

## Reading the matrix

- **S** = separate source-level transport/request implementation **candidate**; distinguishable code exists, but independent authorship/independent *server testing* is **not established**.
- **D** = identifiable derivative/vendored/shared-code lineage. May add client-side extensions, but its copied transport code does **not** independently corroborate server behavior.
- **W** = wrapper/adaptor over another identified API transport; inspect its own event construction, but do not recount the dependency as a second wire implementation.
- **F** = fork/copy sharing exact Git blob(s) or tree with another candidate; no independent confirmation for shared code.
- **X** = inspected candidate without identifiable cloud API source; excluded from protocol claim counts.

All URLs below are pinned to full repository commits and source paths. An unchanged HEAD relative to API-1 does not mean the vendor protocol is unchanged. A source-level S classification is **not** an `API-EV` server-verified classification.

## Reproducible ancestry / negative double-counting evidence

1. **Python `pybhyve` family.** At H and M, `pybhyve/const.py` is the same blob `f71c2ee0614ef8cce18506b1dddab0bbed60e818`; `errors.py` is `6480a10ed68f3008db76084df5dba4674a82fcca`; `typings.py` is `27964836a407e547d89c77e2891a5ed9fdf6bc66`. The MCP `client.py` transport extends the maintained HA-family code (their initial REST and login sections construct the same headers, calls and session fields). This establishes a shared source family without requiring a claim of exact direction/date of copying.
2. **MQTT wrapper.** BM [`package.json`](https://github.com/billchurch/bhyve-mqtt/blob/ac76e9cdc0b4dd232ff1e2c380599208e8e08441/package.json) directly depends on `bhyve-api: ^1.2.4`, and [`src/app.js` line 11](https://github.com/billchurch/bhyve-mqtt/blob/ac76e9cdc0b4dd232ff1e2c380599208e8e08441/src/app.js#L11) imports that package; this is one billchurch transport lineage, not two.
3. **Node MQTT forks.** SF and `a-b/bhyve-mqtt` share HEAD `4462eafb623609eb9f830b1dce21abaa7949beb8` and the same `app/app.js`, `app/orbit.js`, `app/package.json` blobs. `tjmadsen/bhyve-cloudfunction` embeds the identical `orbit.js` blob; wrapper differences do not add independent evidence about that module.
4. **Groovy Hubitat family.** `dcmeglio`, `jpage4500/hubitat-orbitbhyve` and `CalcMan` have matching controller blob `68bc41ae59f8afd591bee86a963b279fb2992799` and driver blobs `7a7c5cb68f00262178faaac888808c0f17c6e0b4`, `d92c7e1455280701e9ecfe5ec3e91267545292e7`. `matthewpetro` has matching drivers, divergent controller blob `052a3b4109a5d9fe44ac49b97ea8dc9c95ff6de4`. Original J's active `hubitat-drivers/orbit-bhyve` files differ from the fork snapshots; examine its deltas rather than claiming a new origin.
5. **Other separate clients.** Distinct HTTP/WS libraries, functions and file organization in Y, D, S, B, V, O, G, WZ, JP, BL, C and Swift support treating them as separate *implementation candidates*; they do not prove their protocol assumptions arose from separate live experiments. Similarity alone is not proof of copying; different languages are not proof of independence.
